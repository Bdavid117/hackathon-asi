Estrategia de pruebas y métricas

Este capítulo respalda el entregable 6 («métricas, escenarios ejecutados, errores observados, limitaciones y resultados de las pruebas de estrés») y las pruebas reproducibles que pide el objetivo 10. La idea central es que el banco de pruebas es un componente del producto, no un añadido de última hora.

De dónde salen los criterios. El enunciado no fija umbrales: los de la columna «Criterio» de las tablas de este capítulo son metas propias del diseño. Incumplir una de ellas se reporta, pero no equivale a incumplir el enunciado. Del mismo modo, usar datos sintéticos y canales simulados es el alcance que permite el §4.7, no una limitación del enunciado; lo que sí se declara como límite es la validez de las cifras (por ejemplo, que el generador y las reglas son del mismo autor).

El banco de pruebas

Generador de datos sintéticos

  • Crea incidentes con verdad de referencia: a qué incidente pertenece cada reporte y qué urgencia real tiene.
  • Aplica ruido controlado: ubicación imprecisa o ausente, texto truncado, duplicados exactos, copias de rumores, contradicciones y pares adversariales (incidentes cercanos pero distintos).
  • Es determinista con una semilla: el mismo escenario produce los mismos datos.

Simulador de canal e inyector de fallos

  • Pérdida (independiente o en ráfagas), duplicación, reorden, retardo con variación, tope de ancho de banda y ventanas que se abren y cierran.
  • kill -9 de un nodo, partición de red, reinicio y relojes desfasados.
  • Un orquestador de escenarios lee un archivo YAML y lo ejecuta de forma reproducible.
# scenarios/s2-kill-node-a.yaml (ejemplo de escenario reproducible)
id: s2-kill-node-a
seed: 42
topology: { nodes: [A, B, C], sync_interval: 5s }
channel:
  loss: 0.40            # pérdida; alternativa: modelo de ráfagas
  duplicate: 0.05
  reorder: 0.10
  delay_ms: [200, 3000]
  window: { open: 3s, closed: 57s }
load:
  generator: synthetic-v1
  incidents: 80
  reports: 1000
  noise: { location_m: 40, truncated_text: 0.10, copies: 0.20, adversarial_pairs: 20 }
faults:
  - { at: 120s, action: kill9,   target: A }
  - { at: 300s, action: restart, target: A }
assert:
  - acked_reports_lost == 0
  - p1_recall >= 0.95
  - false_merge_rate <= 0.01
  - convergence_time <= 60s

El modelo de lenguaje y la reproducibilidad. Como el modelo no es determinista, las pruebas tienen dos modos: reglas (totalmente reproducible) y modelo con respuestas grabadas (se graba una ejecución real y se reproduce). La calidad con modelo real se mide aparte y se reporta como una diferencia respecto al modo de reglas (T12).

Lo que no demuestra. Datos sintéticos del mismo autor que las reglas; una corrida (estos modelos no permiten fijar el muestreo); sólo reportes con texto, y ≈ 38 % de los P1 son SOS sin texto que no pasan por el modelo, así que el criterio de T06 completo sigue sin cumplirse (≈ 85 % global, estimado). Es un intercambio: más P1 capturados a cambio de más reportes P2 subidos un nivel. No hay prueba con reportes reales ni con coordinadores, y T12 sigue con un servidor falso.

Por qué falló y qué no demuestra. Los 5 same equivocados son gemelos adversariales del generador (misma calle, mismo vocabulario, casi a la vez) y los cinco tienen confianza exactamente 0,80, el umbral; cinco uniones malas bastan para casi duplicar la falsa fusión. Que un umbral de 0,85 lo arreglaría es una hipótesis sacada de estos mismos datos (descartaría casi la mitad de las uniones buenas) y exige semillas nuevas. Los textos de T08 son fijos: un caso, no cinco. Con 24 sucesos por conjunto el intervalo de la falsa fusión es ancho; las reglas solas ya pasan del 1 % en estas semillas. Datos sintéticos del mismo autor; una corrida. No hay ninguna llamada al juez desde el nodo.

Informe de resultados (plantilla del entregable 6)

  1. Escenarios ejecutados: archivos YAML con su semilla, versión del código y entorno.
  2. Resultados: tablas y curvas de las métricas anteriores, con la comparación de modo reglas y modo modelo.
  3. Errores observados: fallas reales encontradas durante las pruebas y cómo se resolvieron.
  4. Limitaciones: qué no se probó (canales reales, que el §4.7 no exige; escala real; dispositivos iOS reales) y qué se simplificó.
  5. Reproducción: los comandos exactos para volver a ejecutar cada escenario.

Documentar con honestidad las limitaciones y los errores observados es parte de lo que el enunciado pide y es lo que permite al jurado auditar la solución.
